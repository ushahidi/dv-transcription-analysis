# wav2vec2/CTC ASR benchmark

Baseline word-error-rate (WER) evaluation of open, self-hosted wav2vec2/CTC
checkpoints on this project's African-language test sets - a fourth engine to
compare against [whisper/](../whisper/README.md), [gemini/](../gemini/README.md),
and [chirp/](../chirp/README.md), scored on the same shared FLEURS clips in
[../data/](../data/README.md).

This is the first of the ticket's other named candidates
(`MMS by Meta || Microsoft Research || Think from Nbi || Zindi`) actually
wired up - starting with **Think** (`thinkKenya/wav2vec2-large-xls-r-300m-sw`,
[Hugging Face](https://huggingface.co/thinkKenya/wav2vec2-large-xls-r-300m-sw)):
`Wav2Vec2ForCTC`, Apache 2.0, fine-tuned on Common Voice 11.0 Swahili. Its own
model card reports ~26% WER, but that's on Common Voice's own eval split, not
FLEURS - not directly comparable to the numbers this folder produces. Genuinely
open-weights and self-hostable, unlike Chirp (see [chirp/README.md](../chirp/README.md)).

## Layout

```
wav2vec2/
├── lib/            # shared code - config loading, metrics, CTC model loading
├── scripts/
│   └── run_baseline.py      # WER + confidence report for a wav2vec2/CTC checkpoint
├── english/
│   ├── config.yaml   # facebook/wav2vec2-base-960h - same-architecture control, not the point of the comparison
│   └── results/       # generated by run_baseline.py (gitignored)
└── kiswahili/          # thinkKenya/wav2vec2-large-xls-r-300m-sw
```

## Setup

```powershell
python -m venv .venv
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass   # only if activation is blocked
.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip

# CPU box (this machine):
pip install torch --index-url https://download.pytorch.org/whl/cpu
# GPU box later: pip install torch  (or the CUDA-specific index URL from pytorch.org/get-started/locally)

pip install -r wav2vec2/requirements.txt
```

Same torch/transformers dependency as `whisper/` - unlike `gemini/` and
`chirp/`, there's no lighter install path for a model this folder loads and
runs locally.

## Running the pipeline

```powershell
# 1. Pull the eval set, if not already done - see ../data/README.md. Default
#    'eval' split is several hundred clips (698 for Kiswahili) - use --limit
#    for a quicker/cheaper first pass.
python data/scripts/prepare_dataset.py --language kiswahili --split eval

# 2. Baseline accuracy (WER + confidence)
python wav2vec2/scripts/run_baseline.py --language kiswahili --split eval
python wav2vec2/scripts/run_baseline.py --language kiswahili --limit 100   # first 100 clips only
```

Results land in `wav2vec2/<language>/results/baseline_<model>_<split>.{json,csv}` -
same shape as the other three folders' results files. Confidence here is a
different computation from Whisper's or Gemini's (see
`wav2vec2/lib/model_utils.py`'s `transcribe` docstring) - CTC models don't
generate autoregressively, so there's no equivalent token-by-token generation
probability; this uses the mean max-softmax probability across the frames CTC
decoding actually kept.

A clip that fails outright is recorded with an empty hypothesis and scored as
fully wrong, not dropped - see the module docstring in
`wav2vec2/scripts/run_baseline.py`. If anything failed, the script exits
non-zero even though it still writes full results.

## Why a separate folder, and why it still reuses Whisper's exact normalizer

Same structural independence as `gemini/` and `chirp/` - own
config/metrics/model code, not importing any other folder's `lib/`. The one
thing that *is* shared on purpose is the eval data itself - see
[../data/README.md](../data/README.md); this folder just reads it.

One deliberate difference from `gemini/`/`chirp/`: `wav2vec2/lib/metrics.py`
uses the *same* `transformers`-based `BasicTextNormalizer` as
`whisper/lib/metrics.py`, not jiwer's own transforms. `gemini/`/`chirp/`
avoided that specifically to stay torch/transformers-free - but this folder
already requires the full torch/transformers stack to load the model itself,
so there's no dependency-weight reason to diverge, and using the identical
normalizer keeps WER numbers here genuinely apples-to-apples with the Whisper
baselines.

## Adding another candidate from the ticket

The ticket also names MMS (Meta), a Microsoft Research model, and the Zindi
Swahili ASR challenge's winning solution. If any of those are also
`AutoModelForCTC`-compatible checkpoints on the Hugging Face Hub, they can be
tried with **no code change** - just point `--model` (or `model.name` in
`wav2vec2/kiswahili/config.yaml`) at the checkpoint id.

**MMS is already wired up** (`facebook/mms-1b-all`) - it needed the "genuinely
different inference path" this section originally anticipated: MMS is one
shared `Wav2Vec2ForCTC` backbone plus a small per-language *adapter*, not a
model already fine-tuned for one language like thinkKenya's. Run it with:

```powershell
python wav2vec2/scripts/run_baseline.py --language kiswahili --config wav2vec2/kiswahili/config_mms.yaml
```

Use `--config`, not `--model`, to select MMS: `--model` only swaps the
checkpoint id, not `model.type`/`model.lang_code` (which still come from
whichever `config.yaml` is loaded) - passing an MMS checkpoint via `--model`
against a plain `config.yaml` would load the backbone with no adapter
selected. `run_baseline.py` checks for this specific mismatch and refuses to
run rather than silently producing a broken model, but it's a
name-based heuristic (checkpoint id contains "mms"), not a certainty - the
`--config` form is the reliable way to select it.

**License warning:** `facebook/mms-1b-all` is **CC-BY-NC 4.0 - non-commercial
use only**. It's included here purely as a benchmark data point (the same
role `whisper-large-v3` plays as a reference baseline), **not** as something
cleared for Ushahidi's actual production transcription pipeline. If MMS turns
out to be the best performer, that's a reason to look for a permissively
licensed equivalent, not to ship this checkpoint as-is.

The adapter-loading mechanics (`wav2vec2/lib/config.py`'s `model.type`/
`model.lang_code`, `wav2vec2/lib/model_utils.py`'s `load_model`/
`load_processor`) are generic - any other adapter-based checkpoint can reuse
the same `model.type: mms` path via its own `config_*.yaml`, not just MMS
itself.

## Adding a new language

Create `wav2vec2/<language>/config.yaml` with `language_name` and a
`model.name` pointing at a checkpoint fine-tuned for that language, plus a
matching `data/<language>/config.yaml` (see
[../data/README.md](../data/README.md)) if that language isn't already
downloaded - then rerun the two commands above with `--language <language>`.
